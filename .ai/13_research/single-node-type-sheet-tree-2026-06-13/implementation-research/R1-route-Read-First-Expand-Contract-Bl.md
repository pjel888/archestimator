# Read-First Expand-Contract: Blind the Gates Before You Open the Door

**Thesis:** Make every read path kind-agnostic while the DB still enforces two kinds (a provable prod no-op), then ship the forward-only migration + write/layout/vocab/template relaxation as one atomic lockstep behind a maintenance window with a fresh logical dump, then contract dead code and brittle tests last.

**Point of no return:** The single point of no return is the moment in Phase 2 when the forward-only migration is applied to prod AND a real user persists the first genuine mixed-content node (a node holding both children and estimate_row_items). Up to migration-apply, the fresh Phase-0 logical dump restores cleanly. After the first real mixed-content row exists, re-adding the dropped active-kind checks / area-row triggers / validate_* rows-must-be-area rules will FAIL on real data — the only recovery is restore-from-dump plus replay of everything since the window, which is why the cohort is kept tiny and the window is fenced. Everything in Phases 0, 1, and 3, and all the application code (c/d/e/f) in Phase 2, is git-revertible; only the schema relaxation against real mixed data is irreversible.

**Self-critique:** 1) Phase 2 is a big-bang PR and that is in tension with 'smallest safe blast per PR'. The migration + write + layout + vocab + template + 2 test rewrites genuinely cannot be split (constraint 5 forces template lockstep; relaxing writes without the layout/vocab leaves a broken half-state; the brittle tests break the moment migration text changes), so the single largest, riskiest PR is also the one crossing the irreversible boundary. I mitigate with maintenance window + branch pre-verification + fresh dump + tiny cohort, but reviewability of this PR is the route's weakest point — a reviewer cannot hold all of it in their head, and a subtle write-path or template-trigger defect could slip through and only surface after the no-return line. A partial mitigation I did NOT take: one could land (d) layout + (e) vocab as a cosmetic-only PR BEFORE Phase 2 (they touch no data semantics), shrinking Phase 2 to migration+write+template+tests. I kept them in Phase 2 to avoid a confusing intermediate UI that says 'Area' but still blocks rows-on-group; that is a defensible call but it does inflate the irreversible PR.\n\n2) The route's safety leans hard on the Phase-1 byte-parity claim ('deleting gates is a prod no-op because no node has both children and rows today'). That is true for the estimate tree, but I am trusting the adversarial research that NO production path — including any historical/legacy data or in-flight AI-dormant surface — has already produced a node with both. If even one such node exists in prod data, Phase 1 is NOT a no-op and could itself change totals on a live share. I assert byte-parity-on-real-data as a Phase-1 gate to catch this, but it depends on the verification branch carrying representative prod data, which the disabled-PITR / manual-dump posture makes harder to guarantee.\n\n3) Rollback after the no-return line is theoretical more than practical: 'restore dump + replay' has no automated replay mechanism described, so in reality a serious post-migration defect means manual data reconstruction for affected beta estimates. The route reduces the PROBABILITY of needing rollback (heavy pre-merge branch testing) far more than it improves the EASE of rollback. For a forward-only migration with PITR disabled, that is the honest best case, but it means the maintenance-window smoke test in Phase 2 is doing disproportionate load-bearing work — if it misses a defect that only manifests under real concurrent cohort usage, the safety net is thin."

## Route: Read-First Expand-Contract — "Blind the Gates Before You Open the Door"

### The one idea that orders everything

The data-loss window is a **conjunction**, not a single event. Rows vanish only when BOTH are true at once:

1. the **DB allows** a cost row on a node that also has children, AND
2. a **read path still gates** on `kind === 'area'` (share reconstruct :297, export :265, charts :175/256/309, workshop branch :79, activity scope :427, plus the two guards in estimate-mutations :12 and estimate-tree-data :409 that *throw*).

I verified in the code that today term (1) is false (active-kind checks + area-row triggers still enforce it) and that the read fixes are **gate-deletions on an already-kind-agnostic substrate** (`buildEstimateTree` attaches rows to any node, `computeNodeTotal` sums own+children, `branch.tsx` renders a row table in every node). reconstruct-share-tree.ts:297 literally reads `node.kind === "area" ? (rowsByNodeId.get(node.id) ?? []) : []` — for any non-area node it discards `rowsByNodeId.get(id)`.

So the safe sequence is forced: **drive term (2) to false everywhere while term (1) is still false.** That makes the read fixes a *provable production no-op* — there is no node with both children and rows for the deleted gate to have affected — and it closes the window permanently before the irreversible migration can ever open it.

### Phase shape

- **Phase 0** buys the only rollback artifact that exists under disabled PITR: a *tested, restorable* logical dump, plus a Supabase verification branch and the parity-test skeletons. Nothing ships.
- **Phase 1** deletes every read-path `kind === 'area'` gate in three small revertible PRs (share first — it's the live public path and highest risk — then workshop+domain, then export+charts). The DB still enforces two kinds, so each PR is byte-identical on real data and trivially reversible. Zero user value by design; this is the price of safety. Crucially, includeDescendants is left alone here — only row *emission* at :427 is decoupled, not scope semantics.
- **Phase 2** is the atomic lockstep across the irreversible line: migration (b) + write relaxation (c) + layout (d, including the stable persisted `includeDescendants` per constraint 6) + vocabulary (e) + template parity (f), plus the rewrite of the two brittle contract tests that break the instant migration text changes. Template DB+UI MUST move in this same PR because save-as-template (component-library/actions.ts:768) copies estimate subtrees into template tables — relaxing the estimate side while template triggers still reject rows-on-group breaks that path (constraint 5). It ships behind a maintenance window, after the migration is dry-run on the branch and a *fresh* dump is taken immediately pre-apply. This is the only phase with user value — and it delivers the *entire* feature.
- **Phase 3** contracts: delete the now-dead helpers (canNestEstimateNodeKind, canNodeReceiveRows, wrap-template machinery) and slim the 138-assert source-string test down to behavioral one-kind assertions. Pure subtraction, fully reversible, cannot reopen the window.

### Why this is the safest ordering

Putting reads first means the irreversible migration in Phase 2 lands into an app that *already reads mixed content correctly everywhere*, verified on a branch against a real snapshot. The forward-only hazard (constraint 2) is therefore the *last* risk taken, not the first, and it's taken with the read side already proven, the cohort tiny, writes paused, and a fresh dump in hand. Every phase before the migration-apply is a clean `git revert`; the schema is the single thing that can't come back once real mixed data exists.
