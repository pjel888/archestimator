## How to use this before merging any refactor PR

Before merging **any** performance-refactor PR, an implementer (or a human mid-incident) runs the **doc-27 PR checklist** (the per-PR mechanics: `bun run validate` green, `detect_changes({scope:"compare", base_ref:"main"})` scope-clean, the seam pre-edit checklist of doc 24 §2.3, one-responsibility-per-PR) **and then consults this register** to answer the load-bearing question doc 27 cannot: *does this step change a customer-visible number, structure, or access decision, and is the gate that proves it unchanged actually present and green?* Doc 27 proves the PR is mechanically clean; **this doc proves it is behavior-preserving.** Concretely: (1) find the step's row in §3 (per-phase correctness gate) — if its only gate is render-count, **STOP** (it is INSUFFICIENT, §3); (2) confirm every §1 invariant the step touches has its proof gate green; (3) if anything in §2 ("stop immediately if X") has tripped, do not merge — escalate per §2; (4) confirm the step is a safe pause/revert point via the §4 kill-switch map. This refactor's hard requirement is *do not break anything* — customer financial totals, proposal-export deliverables, share snapshots, tenant isolation. A render-count win that ships a wrong total, a stale export, a broken share snapshot, or a cross-tenant leak is a **failure**, not a win. The four tables below are the objective bar.

## 3. Per-phase correctness gate — INDEPENDENT of render count

The bar: a phase that changes customer-visible numbers/structure must have a **correctness gate that proves the numbers/structure are unchanged**, not merely a render-count gate. A render count proves the app is *fast*; it does NOT prove the app is *correct*. **Any phase whose only gate is render-count is flagged INSUFFICIENT** and must not merge until its correctness gate exists and is green.

## 4. Kill-switch map — which flag reverts which risky step (every step is a safe pause/revert point)

Per doc 24 §5, each risky step lands behind an OFF-by-default flag in the proposed `src/lib/workshop/perf-refactor-flags.ts` (extends the proven `virtualization-flags.ts` pattern, `readPublicFlag(env, default)`). Flipping a flag OFF reverts that step to the old path **without a code revert** — so any flagged step is a safe pause/revert point.

| Risky step | Flag (doc 24 §5) | Env var | Kill-switch effect (revert to OLD path) | Invariant it guards |
|---|---|---|---|---|
| Phase 3 step 2 — per-row editable store | `perRowEditableStore` | `NEXT_PUBLIC_PERF_PER_ROW_STORE` | flip OFF → single `editableRows` `useState` map (memo guards unchanged either way) | I-2 |
| Phase 3 step 3 — incremental totals | `incrementalTotals` | `NEXT_PUBLIC_PERF_INCREMENTAL_TOTALS` | flip OFF → full DFS `computeNodeTotals` (latent fallback `branch.tsx:177` `nodeTotals?.get(id) ?? computeNodeTotal(...)` makes it safe) | I-3 |
| Phase 3 step 5 — resync diff | `resyncDiff` | `NEXT_PUBLIC_PERF_RESYNC_DIFF` | flip OFF → whole-map rebuild on reconcile | I-2 |
| Phase 5 — optimistic adapter (per flow) | `perf-refactor-flags` adapter flag (per-flow cutover, 11 §10) | (per-flow) | flip OFF → that flow's legacy optimistic/rollback path | I-3 (displayed state), §1 I-8 |
| Phase 7 — provider topology move | `workshopScopedProviders` | `NEXT_PUBLIC_PERF_WORKSHOP_PROVIDERS` | flip OFF → root `providers.tsx` mount (guards RISK-19; verify `prove:workshop-auth-boundary`) | I-8 (RISK-19), I-7 |
| Phase 8 — chart RPC cutover | `chartBucketsRpc` | `NEXT_PUBLIC_PERF_CHART_RPC` | flip OFF → JS aggregation path; no DB rollback needed | I-8 (RISK-20) |

**DB two-deploy additive-then-cutover revert (doc 14 §6.1 / 24 §5.4):** DB changes are NOT one-shot. **Deploy N** ships the migration **additively** (RPC/index exists; app does NOT call it) — for `get_project_chart_buckets`, this is **review-and-harden the existing deferred migration** (`supabase/migrations-pending-review/deferred/20260614021500_get_project_chart_buckets_rpc.sql`) by adding the missing `is_workspace_member(...)` join (doc 22 §2.2) before promotion. `CREATE INDEX CONCURRENTLY` runs **non-transactional**, one statement per migration, for clean rollback (14 §6.1). **Deploy N+1** flips `chartBucketsRpc` ON only after `prove:project-chart-buckets` (cross-tenant denial) passes on the deployed RPC. Per-class revert (14 §6.3): FK index → `DROP INDEX CONCURRENTLY`; new RPC → drop function (app keeps JS path); RLS-adjacent → revert policy + re-run `prove:rls-initplan`. A bad RPC is never in the hot path before its denial proof passes, and the app always falls back without a DB rollback. **Feature-flag flip is preferred over `git revert`** (24 §3.3); revert only if a flag does not fully restore behavior.
