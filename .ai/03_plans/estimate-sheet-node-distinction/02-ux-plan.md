# 02 — UX Plan: Group vs Area Distinction in the Estimate Sheet

**Date:** 2026-05-21  
**Scope:** Center estimate sheet (`EstimateSheetContent`) node rendering  
**User persona:** Small contractor / estimator working under time pressure

---

## 1. User mental model

When an estimator looks at the sheet, they think in two categories:

1. **"This is a section / folder / container"** — something that groups work by location, phase, building, or trade. It has sub-sections inside it. It does not directly contain material line items.
2. **"This is a room / area / scope surface"** — the actual place where materials, labor, and costs are assigned. It owns the spreadsheet rows.

The current UI collapses these two mental categories into one visual shape: a 32px-high muted bar with a tiny icon swap. Users must read the icon carefully to know whether clicking the caret will reveal more folders or reveal a cost table.

---

## 2. Hierarchy readability needs

### N2.1 — Scannability at depth

A typical project tree:
```
Lot A (group)
  └── Main House (group)
        └── Ground Floor (group)
              ├── Foyer (area) → [row table]
              ├── Living Area (area) → [row table]
              └── Kitchen (area) → [row table]
```

At 3–4 levels of nesting, the estimator needs to:
- Instantly know whether a header is "organizational" or "work-surface."
- Predict what will appear when they expand it (sub-headers vs row table).
- Trace cost roll-ups upward without reading every label.

### N2.2 — Predictable collapse behavior

- Expanding a **group** should reveal more headers (possibly mixed groups and areas).
- Expanding an **area** should reveal the row-item table or an empty drop zone.
- The header styling should telegraph this difference before the user clicks.

### N2.3 — Cost attribution confidence

Users must trust that a total shown on a group header is a **roll-up sum**, while a total on an area header is a **direct sum of its rows**. The visual system should reinforce this semantic difference.

---

## 3. Node codes: user mental model

### Why codes matter

Estimators do not think in names alone. They think in:
- **WBS codes** (Work Breakdown Structure): `1.2.3`
- **CSI MasterFormat**: `03-1000` (Concrete), `09-3000` (Tile)
- **Location codes**: `A-01-GF-LR` (Lot A, Building 01, Ground Floor, Living Room)
- **Custom project codes**: whatever the client or contract specifies

A code provides **stable reference** across revisions, proposals, and change orders. Names can change; codes should not.

### Code generation modes

| Mode | User effort | Use case |
|------|-------------|----------|
| **Auto (hierarchical)** | Zero | Fast project bootstrap; code reflects tree position (`01`, `01.01`, `01.01.01`). |
| **Auto (kind-based)** | Zero | Prefix by kind: `G-01` (group), `A-01` (area). |
| **User-defined** | Medium | Contract-specific or client-mandated numbering. |
| **Mixed** | Low | Auto-generated by default; user can override. |

**Recommendation:** Start with **auto hierarchical** (frontend-only, no DB column needed). Add user-defined persistence later.

### Code placement in the header

The code must be visible at a glance but must not compete with the node name or total. It should read as **metadata**, not primary content.

Placement: inline prefix before the name, in a monospace/tabular font, slightly smaller and subdued.

```
▼ 📁 01.01   Main House                ₱3.1M
     ↑ code   ↑ name                   ↑ total
```

### Breadcrumb necessity

When an area node is expanded, the estimator sees its row table. The row table contains materials, quantities, and costs. The estimator needs to answer: **"Which room/building/lot is this?"** without scrolling up to trace indentation.

A breadcrumb below the area header provides this context:
```
Lot A › Main House › Ground Floor
```

**Rules:**
- Breadcrumbs are **area-only**. Groups already show their children; their context is visually implicit.
- Breadcrumbs are **not interactive**. They are read-only context, not navigation.
- Breadcrumbs truncate with ellipsis if the path is long.

## 4. Distinction strategies (ranked by UX impact)

### Strategy A: Container vs Surface background semantics

**Rationale:** Background is the largest surface area and the fastest signal.

- **Group = "container"** → Muted background (`bg-surfaceMuted`) with full border. Looks like a folder/card that holds things.
- **Area = "surface"** → White background (`bg-white`) with only a bottom divider. Looks like it belongs to the sheet/paper below it.

**Impact:** High. Changes the atmospheric reading of each node type immediately.

### Strategy B: Typography weight hierarchy

**Rationale:** Weight communicates structural importance without consuming space.

- **Group name** → `font-semibold` or `font-bold`. It is a navigational/structural landmark.
- **Area name** → `font-normal` or `font-medium`. It is content/work data.

**Impact:** Medium-High. Reinforces Strategy A at the text level.

### Strategy C: Left border accent

**Rationale:** Left borders are scanned quickly by the eye and map to "indentation + hierarchy."

- **Group** → Subtle left border `border-l-2 border-l-divider` to mark it as an organizational boundary.
- **Area** → No left border (the row table below already has its own `border-l-2 border-l-accent/70` on material cells).

**Impact:** Medium. Helps at deep nesting where indentation alone is tiring.

### Strategy D: Kind badge (micro-label)

**Rationale:** Explicit labels remove ambiguity completely.

- A 8px uppercase tracking-widest pill/badge next to the name or at the right edge of the header.
- Text: "GROUP" / "AREA" or shortened "GRP" / "AREA".
- Color: `text-tertiary` with `border-hairline bg-white` (neutral, not colorful).

**Impact:** Medium. Explicit but risks clutter at small sizes. Should be tested for density tolerance.

### Strategy E: Vertical connector lines for nested children

**Rationale:** Helps trace parent-child relationships when indentation is deep.

- A 1px `border-l-hairline` guide running down the left side of child content, aligned with the parent's text column.
- Only visible when a group is expanded and has children.

**Impact:** Low-Medium. Nice-to-have for deep trees; not essential for the group/area distinction itself. May be deferred to a second phase.

## 4. Interaction design

### 4.1 Hover states

Both header types share the same hover behavior (subtle background shift) to keep the interaction model simple:

- **Group hover:** `hover:bg-[#EAEEF3]` (slightly darker than `bg-surfaceMuted`).
- **Area hover:** `hover:bg-surfaceMuted/60` (subtle tint on white).

### 4.2 Focus and keyboard

- Focus ring uses existing pattern: `focus-visible:ring-2 focus-visible:ring-[#c8d2df]`.
- No differentiation needed between group and area focus states; focus is about the interactive element, not the node type.

### 4.3 Collapse/expand

- The caret button remains on both types. For areas, collapsing hides the row table. For groups, collapsing hides children.
- **UX requirement:** The caret for an area with zero rows AND zero children should still be present but may be visually subdued (e.g., `text-hairline`) to indicate there is nothing to expand. Currently this state is handled by `hasContents` — if false, the empty area message is shown but the section is still expandable. This behavior is acceptable; the visual distinction will make the "empty area" state obvious.

### 4.4 Drag and drop target feedback

- When dragging a library item over an **area** header or its table, the existing blue accent feedback (`bg-[#EFF6FF]`, `border-l-accent/70`) is sufficient.
- **Group nodes should NOT show drop acceptance for library items.** They already reject drops at the data layer, but the visual layer should reinforce this by not highlighting group headers during library-item drags.

---

## 5. Accessibility

### 5.1 Screen reader

- Each `EstimateSheetBranch` `<section>` already has `aria-label={node.name}`.
- **Add:** `aria-roledescription` or descriptive label to communicate kind:
  - Group: `aria-label={`${node.name}, group`}`
  - Area: `aria-label={`${node.name}, area`}`
- The collapse button already has `aria-expanded`. Ensure the `aria-label` includes the node kind: `"Collapse Foyer area"` / `"Expand Main House group"`.

### 5.2 Color independence

- The distinction must not rely on color alone (WCAG 1.4.1).
- Background difference (container vs surface) + typography weight + icon shape + optional badge provide multiple independent channels.

### 5.3 Reduced motion

- No animation changes are introduced. Existing `transition` classes on backgrounds are acceptable.

---

## 6. Deferred (out of scope for this plan)

- Vertical connector lines (Strategy E) — can be added later without breaking the group/area distinction.
- Row-table restyling — the row table already has strong visual identity; only the header above it changes.
- Multi-select or bulk operations on headers.
- Inline renaming in the sheet (rename is currently tree-only).

---

## 7. UX acceptance criteria

1. A user scrolling the estimate sheet can identify whether a header is a group or an area **without reading the icon** (using background, weight, or border cues).
2. A user with color-vision deficiency can distinguish group from area via background treatment and typography weight.
3. Expanding a group predictably reveals nested headers; expanding an area predictably reveals a row table or empty drop zone.
4. Screen-reader users hear the node kind announced with the node name.
5. The distinction does not increase the perceived density or reduce the scannability of row-item costs.
