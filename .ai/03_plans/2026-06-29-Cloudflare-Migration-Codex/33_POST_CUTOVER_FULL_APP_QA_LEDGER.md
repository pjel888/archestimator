## Provider Downgrade Boundary

Current technical evidence supports keeping production traffic on Cloudflare for closed beta and keeping Vercel/Supabase/Resend at lowest-cost/rollback posture.

As of 2026-07-02, the app-side runtime is Cloudflare-first: hosting is Cloudflare Worker/OpenNext, app/auth data is Cloudflare D1 + Better Auth, media is Cloudflare R2, realtime collaboration is Cloudflare Durable Objects, DNS/custom-domain serving is Cloudflare, and outbound app email proof is through Cloudflare Email. The remaining provider work is operational cleanup, not active app migration.

Cloudflare for Platforms / Workers for Platforms is **not** part of the current estimate-sheet user model. Archestimator users, collaborators, recipients, and closed-beta access should stay in the app's Better Auth + D1 workspace/project membership model. Consider Cloudflare for Platforms later only if Archestimator needs customer-owned custom domains, tenant-managed deployment surfaces, or per-tenant extension/runtime isolation beyond normal app collaboration. Reference surfaces: `https://www.cloudflare.com/solutions/platforms/` and `https://developers.cloudflare.com/cloudflare-for-platforms/`.

Recommended current posture:

- Vercel: keep dormant/rollback access and deployment/env history snapshots until the Cloudflare observation window is accepted; no production traffic should depend on Vercel.
- Supabase: keep backup/export access until final logical export/readback and rollback consequence are accepted; active app/auth data should stay on Cloudflare D1.
- Resend: keep account/API-key cleanup as an explicit ops step after final mail proof; app email proof is through Cloudflare Email, and Resend should not be an active runtime dependency.
- Namecheap/DNS: keep Cloudflare nameserver/DNS delegation as the active path; avoid registrar-side destructive changes unless a separate domain recovery plan exists.

Do **not** delete provider projects, DNS records, backups, keys, buckets, auth data, or invoices from Vercel/Supabase/Resend until a separate provider-cleanup runbook verifies:

- final exports/backups are available and restorable or intentionally waived;
- no production env/secrets reference the old provider;
- no support/legal/audit record needs old dashboard access;
- owner accepts the rollback consequence;
- account cancellation/downgrade steps are performed intentionally in provider dashboards.
