## Decision tree (apply per unsafe mutation)

1. Does the mutation have natural uniqueness (e.g., one decision per share per recipient)? **Yes** → use natural uniqueness; no idempotency-key ledger needed.
2. Does it use `If-Match` / `If-None-Match` / explicit expected revision? **Yes** → record as lost-update strategy; no idempotency-key ledger needed.
3. Is it stateless (same input always produces same observable result, no side-effect accumulation)? **Yes** → mark `naturally-idempotent`; no ledger needed.
4. Is it async-accepted (returns 202, side effect completes via queue/cron)? **Yes** → defer to at-least-once matrix; queue dedupe is the authority.
5. Otherwise → idempotency-key ledger required. Define key source/scope/TTL/storage/fingerprint/replay/mismatch/concurrent-duplicate/failure-replay.

## Lost-update protection strategy catalog

| Strategy | Where to apply | Implementation hint |
|---|---|---|
| `If-Match` / `If-None-Match` HTTP preconditions | Route Handlers with ETag-able resources | `etag()` + `If-Match` header check; 412 on mismatch |
| Explicit `expectedRevision` / `expectedVersion` in body | Server Actions on aggregate roots | Compare-and-swap in D1 UPDATE; 409 on mismatch |
| Natural uniqueness (composite unique constraint) | Per-recipient-per-share decisions, per-invite acceptance | D1 UNIQUE constraint; INSERT … ON CONFLICT DO NOTHING |
| Optimistic concurrency control (CAS) | Estimate mutations | Already partially in `d1-action-client.ts` |
| No-conflict reason (documented) | Stateless mutations, monotonic state transitions | Document in this matrix; no enforcement needed |

## Privacy review gates (BLOCK new ledger creation)

Before any new D1 ledger table is created (idempotency, ticket nonce, audit expansion), the following must be answered and recorded in `runtime-store-ledger.md`:

1. Data classes covered (personal data when linked? sensitive pseudonymous?)
2. Lawful basis (legitimate interest / contract / consent)
3. Retention period (default 24h ordinary, 7d high-value async)
4. DSAR/delete/anonymize rule (per-row delete vs aggregate anonymize)
5. Provider retention (D1 backups include these rows — what's the restore-time impact?)
6. Security exception policy (extended retention for incident investigation?)
