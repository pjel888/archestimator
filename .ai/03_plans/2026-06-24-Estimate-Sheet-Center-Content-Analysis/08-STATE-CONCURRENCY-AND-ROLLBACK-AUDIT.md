# 08 — State, Concurrency, and Rollback

## State machine

The center sheet's runtime state is a product of many mostly-orthogonal axes. The orchestrator (`EstimateSheetContent.tsx`) bundles them into a single reducer (`estimateSheetContentReducer` l. 1001-1019) keyed by field name.

### Critical invariants

1. **Only one `pendingLibraryCommitGate` at a time** — opening a new one while another exists overwrites it silently. The modal renders from a single key (l. 3126). Two concurrent trust-gates are NOT supported.
2. **`activeExpressRowId` is per-table** (`EstimateRowItemsTable` local state, l. 534), not per-sheet. Two areas' tables each track their own active editor. But because virtualization flips off for THAT table when any editor is active (l. 545-546), 1,000-row area + editor = unvirtualized.
3. **Per-row save state is shared** — one `saveState` field in `useSaveState` (l. 204-253) ref-counts via `activeMutationCount` but the public `saveState` is the latest transition. This is the root of ESC-P1-04.
4. **`historyRequestGenerationRef`** (l. 1526) ensures stale activity-history fetches are dropped on scope change. Pattern: increment generation, capture, compare in `.then` callback (l. 2038-2071).
5. **`skipEditableRowsSyncRef`** (l. 1364) — bumped on every `setEstimateTree` to prevent the editable-rows-collection effect (l. 2130-2147) from overwriting an in-flight cell edit when a new server tree arrives. The skip counter is consumed (decremented) once per bump.

## Mutation queues

Per-row queue: `rowUpdateQueuesRef: Record<rowId, Promise>` at `use-estimate-row-mutations.ts:273`.

`enqueueRowMutation` (l. 530-539) chains each new mutation behind the previous one for the same row:

```ts
const previousUpdate = rowUpdateQueuesRef.current[rowId] ?? Promise.resolve();
const nextUpdate = previousUpdate.catch(() => undefined).then(run);
rowUpdateQueuesRef.current[rowId] = nextUpdate;
```

This ensures row A's mutations serialize (update quantity, then update name, then delete — all run in order). But **row A's queue and row B's queue run in parallel**, which is the root of ESC-P0-01 and ESC-P1-03.

`enqueueRowUpdate` (l. 541-543) wraps `updateMutation.mutateAsync(withMutationIdentity(input))` and `getCachedRowRevision(rowId)` (l. 509-513) seeds the optimistic-concurrency check.

`withMutationIdentity` (l. 515-521) attaches `mutationId` (generated by `createMutationId`, l. 198-202) and `expectedRowRevision` (from cache). Server action `updateEstimateRowItem` uses these for idempotency and conflict detection.

## Tree revisions

Tree-level optimistic concurrency via a SEPARATE revision counter:

- `getTreeRevision` returns `queryClient.getQueryData<number>(revisionKey)` (`use-estimate-query.ts:51, 114`).
- `bumpTreeRevision` increments on every `setTree` call that actually changes the tree (l. 52-59, 115-122).
- `restore(previousTree, expectedRevision)` (l. 71-76, 134-139) only applies the previous tree if the current revision still matches `expectedRevision`. This prevents a stale rollback from clobbering a newer change.

This revision gate is what makes the template-insert optimistic flow safe:

```ts
const nextRevision = setEstimateTree(...);  // bumps revision
// ... RPC ...
if (getEstimateTreeRevision() === nextRevision) setEstimateTree(() => result.tree);
else restoreEstimateState(previousTree, previousRows, nextRevision);  // rolls back because revision drifted
```

`insertTemplateIntoParent` (l. 2425-2464), `insertTemplatesIntoParent` (l. 2470-2507), `insertTemplateNodeIntoParent` (l. 2580-2617) all use this pattern correctly.

**`insertProjectSourceIntoParentById` (l. 2533-2561) does NOT** — this is ESC-P0-02.

## Rollback paths (per action)

| Action | Rollback trigger | Rollback implementation | Atomic? |
|--------|------------------|-------------------------|---------|
| Insert library item | `insertMutation.onError` | `restoreEstimateState(previousTree, previousRows, rollbackRevision)` (l. 2241) | YES |
| Insert library item (express draft) | `handleExpressInsertError` → draft status `failed` | UI shows retry/delete buttons (cells.tsx l. 195-225); no auto-rollback | YES (eventual) |
| Replace row item | `replaceMutation.onError` | Same `restoreEstimateState` (l. 2757) | YES |
| Update row item (blur) | `updateMutation.onError` | `restoreEstimateState(previousTree, previousRows, rollbackRevision)` (l. 2241) | YES |
| Delete row | `deleteMutation.onError` | `restoreEstimateRowItemAtLocation(tree, previousRowLocation)` (l. 3057) | YES |
| Detach (Make Project Specific) | `detachMutation.onError` | `restoreEstimateState(...)` (l. 2961) | YES |
| Promote to library | `promoteMutation.onError` | `restoreEstimateState(...)` (l. 2909) | YES |
| Insert template (single/batch/node) | `.catch(error)` on promise | `restoreEstimateState(previousTree, previousRows, nextRevision ?? rollbackRevision)` (l. 2458, 2501, 2611) | YES |
| Insert project source | `.catch(error)` | toast only — no rollback needed (non-optimistic) | YES |
| **Move component** | **per-row `replaceMutation.onError`** | **`restoreTargetRow` OR `restoreSourceRow` independently (l. 3025, 3034)** | **NO — partial rollback** |
| **Bulk delete** | **per-row `deleteMutation.onError`** | **per-row `restoreEstimateRowItemAtLocation`** | **NO — partial rollback** |
| Tab create/rename/delete/duplicate/reorder | per-action `.catch` | Tab strip reconciles from server-returned tab list | YES |

## Stale response handling

Three mechanisms:

1. **Per-row operation-id** (`rowOperationIdsRef`, l. 272, 454): `updateMutation.onSuccess` (l. 484-494) checks `rowOperationIdsRef.current[input.rowId] !== context.operationId` and returns early if a newer operation superseded this one. Same check in `onError` (l. 495-496). This prevents an older response from patching a row that has since been edited again.
2. **Tree revision** (above): prevents older full-tree responses from clobbering newer optimistic changes.
3. **History request generation** (`historyRequestGenerationRef`, l. 1526): per-scope generation counter; stale `.then` callbacks short-circuit.

The first two protect row/tree mutations. The third protects activity history. **Project-source insertion bypasses the second** (ESC-P0-02).

## Collaboration conflict handling

- **Row revision conflicts** (`EstimateRowRevisionConflictError`, `row-revision-conflict.ts`): server throws a 409 with code `ESTIMATE_ROW_REVISION_CONFLICT_CODE`. Client `readMutationErrorCode` (l. 26-30) extracts the code; `useEstimateRowMutations` `onError` (l. 293-298, 335-340, 356-361, 442-447) triggers `invalidateTreeAfterMutationError` which **forces an active refetch** (`refetchType: "active"`) for revision conflicts so the user sees the canonical state.
- **No silent last-write-wins**: the revision check is enforced server-side via `expected_row_revision` RPC param.
- **Cursors are not edit locks**: remote cursors are awareness only (`useEstimateCursorCollaboration`); no optimistic locking based on cursor presence.

## Partial-failure scenarios

### Scenario: insert library item while a previous insert is in flight

- Per-row queue serializes if same target node; the second insert lands in `pendingPayloadRef`-style queue (`rowUpdateQueuesRef`).
- Different target nodes run in parallel; both succeed or fail independently.
- **Risk**: if both target the SAME row (impossible via UI but theoretically possible via API), the second's `expected_row_revision` would 409.

### Scenario: update row while a replace is in flight

- Per-row queue serializes them.
- `replaceMutation.onSuccess` patches the cache with the full canonical row (l. 343-362), which includes any in-flight update's effect if the server applied it.
- `updateMutation.onSuccess` checks `rowOperationIdsRef` (l. 485) and short-circuits if the replace superseded it.

### Scenario: delete row while a replace is in flight

- Per-row queue: replace resolves first, then delete fires against the replaced row.
- Both call `deleteRow`/`replaceRow` with their own `expectedRowRevision`; server enforces.

### Scenario: move component while target row is being edited

- The target's pending update is in its queue; move's `replaceRow(target)` queues behind it.
- The user's edit either lands first (revision N) or the move lands first (revision N); the loser gets a 409.
- On 409, `invalidateTreeAfterMutationError` refetches the tree → user sees the canonical state.
- **But the OTHER row's mutation (source-clear) is unaffected** — this is the partial-failure window of ESC-P0-01.

### Scenario: project source insert while a template insert is in flight

- Both call `setEstimateTree` on success.
- Template's success is gated on `getEstimateTreeRevision() === nextRevision` — if the project-source landed first, the revision drifted and the template's `.then` reconciles via the gate.
- Project-source's success is NOT gated — it overwrites whatever the template just did. **This is ESC-P0-02.**

### Scenario: tab switch while a row mutation is in flight

- The mutation's query key is the OLD tab's tree; when it resolves, `setQueryData` patches the OLD tab's cache. The new tab's cache is unaffected.
- **Safe** — per-tab query keys (`estimateQueryKeys.tabTree(estimateId, tabId)`) isolate caches.
- **Caveat**: the mutation's `invalidateQueries({ queryKey, refetchType: "none" })` (l. 290-291, 332, 353, 403, 429, 446, 491, 505) marks the OLD tab stale; if the user returns to it, they get a fresh fetch.
