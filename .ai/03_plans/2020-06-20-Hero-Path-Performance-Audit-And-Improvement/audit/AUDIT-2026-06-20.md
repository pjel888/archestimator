## TL;DR — the most important finding

**The hero path's local slowness is network-bound, not code-bound.** A single round-trip from this dev machine to hosted Supabase measured **0.3–5 s** (TLS connect alone hit 5 s once; a trivial REST call 0.3–1.8 s). The database itself executes the hero queries in **<1 ms** (verified in-region via the Supabase MCP `EXPLAIN ANALYZE`). Each authenticated hero route makes several **sequential** Supabase calls (auth `getUser` + data), so over this residential link the routes take **4–10 s** locally. The unauthenticated `/login` route served in **4–17 ms**, proving the Next.js server itself is fast.

In production (Vercel running in/near the Supabase region) each round-trip is ~1–10 ms instead of 100–5000 ms, so the same routes should render in tens-to-low-hundreds of ms. **Local `next start` on a residential connection to hosted Supabase cannot prove (or disprove) production speed** — the dev→Supabase network latency dominates and is ~50–100× worse than in-region production.

**Implication:** the hero path is very likely already production-grade fast in real production. To *prove* it, measure the deployed Vercel app (in-region), not local `next start`. The code-level wins below still help — especially anything that reduces the *number* of sequential round-trips, which helps in every environment.

## Honest caveats

- Local absolute numbers are pessimistic and noisy (busy dev machine + residential→hosted-Supabase latency). Relative/round-trip-count comparisons are more trustworthy than local wall-clock.
- No production/hosted measurement has been taken yet. The "production-grade fast" claim is **not yet proven** — it is strongly *inferred* from the in-region <1 ms DB execution + the fact that local cost is network RTT that production does not pay.
