## 2. Safe-to-change (LOW blast radius) — sheet-owned, easy to test

These are owned almost exclusively by the sheet path and have either dedicated tests or no external consumers:

1. **Add `src/app/workshop/projects/[projectId]/estimates/[nodeId]/loading.tsx`** (NEW file).
   - Zero existing consumers (file doesn't exist). Pure addition. This is the single highest-leverage, lowest-risk change in the plan: it eliminates the cascade where `[projectId]/loading.tsx` (the dashboard shell skeleton) flashes on the sheet route.
   - Risk: must visually match the glass estimate sheet's first paint (avoid CLS / hydration mismatch). Mirror `EstimateWorkspaceClient`'s shell scaffold or a new `EstimateSheetSkeleton`.
2. **`ProjectEstimatesListSkeleton`** — scoped to estimates-list loading only, double-tested (`project-estimates-list-skeleton.test.tsx` behavioral + `project-dashboard-route-shell-ui.test.ts` governance).
3. **`resolveEstimateTabRouteContext`**, **`resolveEstimateEditCapability`** — single sheet-page consumer each; already parallelized in the first `Promise.all` (`page.tsx:36-41`) and second `Promise.all` (`page.tsx:64-71`). Safe to refactor signature/return shape as long as the source-text tests are updated in lockstep (3 files assert on the call shape).
4. **`EstimateWorkspaceClient`** — single consumer (the sheet page). The TanStack tab-cache reconciliation is behaviorally tested. Query-pattern changes are caught by `estimate-workspace-client-cache.test.tsx`; **but** hydration/client-only issues need `next build` + a live smoke (per `[use-server-exports-only-async]`).
5. **`ProjectMiniSidebar`** — already returns `null` on the sheet route; changes barely touch the sheet.
6. **`src/app/workshop/projects/[projectId]/estimates/[nodeId]/page.tsx`** itself — route-local but every change trips ≥3 source-text assertions; treat tests as compile errors and update them in the same commit.

## 3. Risky (HIGH / CRITICAL blast radius) — shared; changes ripple

Ordered by danger:

1. **`WorkshopPageShell` (CRITICAL)** — 11 route consumers + 5 test files. Any change to its `getCurrentUserContext`/`ensureDefaultWorkspace`/`listMainSidebarFavoriteProjects`/`cookies()` awaits, or to its in-shell `<Suspense fallback={<WorkshopShellContentFallback />}>`, shifts first paint on **11 routes** (every workshop page). This is the shell that wraps the sheet via the project layout. **Do not** move its awaits around without a cross-route smoke.
2. **`src/app/workshop/layout.tsx` (HIGH)** — gates every `/workshop/**` route (terms + auth). Already minimal (`return children` after the gate). The terms-status call is sequential after `getCurrentUserContext`; parallelizing them is theoretically safe (both are `cache()`-memoized) but changes first-paint timing for the whole workshop, not just the sheet. `tests/vitest/live-estimate-node-route.test.ts` locks the `react-complex-tree/lib/style-modern.css` import — preserve it.
3. **`src/app/workshop/projects/[projectId]/layout.tsx` (HIGH)** — shared by 4 child routes (dashboard, estimates list, sheet, data). Its `<Suspense fallback={<ProjectRouteContentFallback />}>` wrapping `{children}` is the **direct mechanical cause** of the wrong-skeleton symptom: when the sheet page is resolving, this fallback paints. The streaming `<Suspense fallback={<ProjectHeaderChromeSkeleton />}><ProjectChromeAsync/></Suspense>` wiring is **test-locked** by `project-chrome-streaming.test.ts` — do not change that contract casually.
4. **`StaticWorkshopLoadingShell` (HIGH)** — 4 loading files (workshop root, onboarding, settings, projects list) depend on its chrome. A visual change shows on 4 routes.
5. **`ProjectRouteContentFallback` (HIGH)** — the in-layout Suspense fallback for all 4 project child routes. Cannot be deleted (layout needs a fallback); can only be *replaced per-route* by adding closer `loading.tsx` boundaries (which is exactly what the plan should recommend for `[nodeId]/`).
6. **`ProjectHeaderChromeSkeleton` / `ProjectChromeAsync` (HIGH)** — visible on every project child route. The skeleton's single-wrapper node-count contract is load-bearing against a hydration mismatch (`ProjectChromeAsync.tsx:44-52`); adding/removing children breaks the streaming swap.
7. **`src/app/workshop/projects/[projectId]/loading.tsx` (HIGH leverage)** — this is the skeleton that currently flashes on the sheet route. Editing it shifts the dashboard, data, and estimates-list routes too. Preferred fix is **adding** a closer `[nodeId]/loading.tsx`, not editing this file.
8. **`getCurrentWorkspaceProject` / `getCurrentUserContext` / `requireCurrentUserContext` (HIGH/CRITICAL)** — cannot be *removed*; only their *call ordering* is in scope. All three are `cache()`-memoized (verified for the first two; `requireCurrentUserContext` UNVERIFIED but almost certainly shares the `getCurrentUserContext` resolution) so parallelizing them in a single `Promise.all` is free **as long as the cache key matches**. `requireCurrentUserContext` has **30 consumers** — never change its signature.

## 4. Test-coverage gaps (must scaffold before changing)

Symbols/behaviors with **no direct test** (the regression risk lives here):

- **`src/app/workshop/loading.tsx`** — no behavioral or source-text test.
- **`src/app/workshop/projects/loading.tsx`** — no test (and `ProjectsListSkeleton`, its main import, also has **no test**).
- **`src/app/workshop/projects/[projectId]/loading.tsx`** — exported by fixtures but no assertion on its content. **This is the skeleton that flashes on the sheet route today — adding a regression test that asserts "[projectId]/loading must NOT render on /estimates/[nodeId]" (or that a closer `[nodeId]/loading.tsx` exists) is the single most valuable scaffolding step.**
- **`StaticWorkshopLoadingShell`** — only a passing text mention in `reset-baseline.test.ts`. No behavioral test of its props (title/eyebrow/showEyebrow/hideTitle/contentClassName/alignChromeToProjectSidebar).
- **`ProjectsListSkeleton`** — no test at all.
- **The visual sequence of loading skeletons on the sheet nav path** — no integration test walks `/workshop → /projects → /[projectId] → /estimates → /estimates/[nodeId]` and asserts which skeleton paints at each hop. This is the core symptom and it has **zero coverage**.
- **No `loading.tsx` existence/shape governance** for the `[nodeId]` segment (the missing file).
- **React `cache()` scope assumption** — no test asserts that `getCurrentWorkspaceProject`, `getCurrentUserContext`, `getCurrentUserTermsAcceptanceStatus`, `getEstimateTabs`, `resolveEstimateEditCapability`, `resolveEstimateTabRouteContext` are actually memoized per-request. If anyone removes a `cache()` wrapper thinking the function is only called once, parallelization silently becomes a re-query. **Verify the `cache()` wrapping (rg line numbers above) before recommending parallelization.**

## 5. Cross-route coupling warnings

1. **`[projectId]/loading.tsx` is shared by 4 routes.** Any edit changes the loading appearance on the project dashboard, data page, estimates list, **and** the sheet route (until a closer boundary is added). Prefer *adding* a closer boundary over *editing* the shared one.
2. **`ProjectRouteContentFallback` is the in-layout Suspense fallback for all 4 project child routes.** If the plan recommends replacing it on the sheet route, the replacement must be a **closer Suspense boundary or `loading.tsx`**, not an edit to this component — editing it shifts the dashboard, data, and estimates-list fallbacks too.
3. **`StaticWorkshopLoadingShell` props drive 4 different routes' chrome.** Changing default padding/title rendering/`alignChromeToProjectSidebar` shifts workshop root, onboarding, settings, and projects-list loading visuals together.
4. **`WorkshopPageShell`'s in-shell `<Suspense fallback={<WorkshopShellContentFallback/>}>` wraps `{children}` for 11 routes.** Moving that Suspense boundary, or changing `WorkshopShellContentFallback`, ripples to every workshop page.
