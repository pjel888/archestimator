## Why this exists

Philip wants Archestimator users to type natural-language instructions such as:

> I have a 3 bedroom house project, 1 floor. Please create the project and fill up the sheets and the estimate sheet as well, fill up the components. I only have 5 million pesos for my budget.

The target experience is not a generic chatbot. It is an estimating copilot that can understand project intent, use the user's own projects/library/templates, create a sensible project/estimate/tree/row draft, and stay strictly inside that user's authenticated workspace data.

## Non-negotiable constraints

- This pack began as a readiness-only planning task. Current implementation work is now authorized by explicit user request and must keep this pack updated as product reality changes.
- The model must never receive broad database credentials, service-role keys, arbitrary SQL access, or cross-workspace data.
- AI reads and writes must execute through server-owned, user-scoped, RLS-backed app tools.
- Every write-capable tool must validate workspace/project/estimate ownership at the server or database boundary.
- The MVP should use grounding, tool calling, structured outputs, and evals before considering fine-tuning.
- The first launch should require user confirmation before writes that create, update, delete, or materially price estimate data.

## Current implementation status

As of 2026-05-28, Ask Flip has a first package-builder path:

- `/api/ai/ask` remains the read-only Ask route and now uses intent-gated, compact server-derived context for authenticated Supabase workspace users, including exact project counts for count questions, bounded project labels for project-list questions, compact component-library matches plus active price-option values for component/library/price questions, compact reusable-template matches with bounded area names and row previews for template questions, compact historical estimate-row matches for prior-row/other-project usage questions, validated current-route project/estimate labels for route questions, and compact current-estimate tree/row/total context from the active estimate route.
- `/api/ai/package-builder` handles package-builder `draft`, bounded pre-Apply `refine`, metadata-only rejected-draft `feedback`, and `apply` modes. Refine returns a normal reviewable draft response; feedback records a verified rejection signal only; neither is a production write mode.
- Draft mode builds a reviewable package draft from compact authenticated read-tool summaries plus optional DeepSeek structured hints and deterministic server-side fallback logic. The deterministic fallback now recognizes 3-bedroom condo/unit prompts, creates bedroom plus toilet/bath Area Nodes, folds in bounded matched template area names as structure hints, can reuse matched scoped library components for repeated requirements such as beds and wardrobes in bedrooms plus water closets and lavatories in toilet/bath areas, can use linked prior-project component usage as a ranking hint when choosing between otherwise similar scoped library components, can fan out Living/Dining rooms across multiple tightly matched scoped library components, can use matched prior estimate rows from accessible workspace projects as reviewed allowance precedents when live library components are missing, can use bounded matched estimate-template row previews as review-required allowance rows for package creation, and can build current-route direct template row-copy drafts through a separate `templateRowCopyDraft` contract. Draft read searches use the full bounded package vocabulary so generic condo prompts can still discover bedroom, wardrobe, kitchen, water-closet, lavatory/basin/sink/faucet, living, dining, furniture, console, table, sofa, chair, pendant, lounge, light, fixture, paint, tile, bathroom, sanitary, finish, and general app data before deterministic scoring. Generic rooms such as Living and Dining can now use multiple matched library rows first, then matched prior-project rows as reviewed allowance precedents before falling back to generated allowances. Provider `searchTerms` are normalized, capped, and used only as row-planning hints against already-retrieved scoped component matches; they do not authorize model-directed SQL or broad retrieval. Draft provider context may include bounded portfolio project labels and current project estimate summaries; when a prompt is sent from a project/estimate route it may also include provider-safe current project name, estimate summary, area names/paths, and compact current area rows. Raw project/estimate/node/row ids and client/location details are not sent to the provider.
- `fill_current_estimate` Draft/Apply is now a distinct target-aware contract for prompts such as "Fill this estimate with beds and water closets" from a current project/estimate route. It targets the route-resolved existing estimate, including selected-node URL contexts where the server resolves the owning estimate from `selectedNodeId` and excludes that active estimate from historical precedent reads. It inserts reviewed rows into existing Area Nodes, uses the signed draft token plus explicit confirmation, and calls the existing authenticated `insert_estimate_row_item_with_history` RPC per row with deterministic row correlation ids. If the route estimate has no Area Nodes but has an existing Group Node parent, Draft stays in `fill_current_estimate`, creates missing Area Node drafts under that existing group, and Apply creates those Area Nodes through `create_estimate_node_with_history` before inserting rows. Current-route update prompts such as "Change the existing bed quantity to 2" can now produce `update_existing_row` drafts for quantity, Misc Cost, and contingency changes against matched current estimate rows; Apply calls `update_estimate_row_item_with_history` with the row's expected revision. Current-route replacement prompts such as "Replace the existing bed row with the Queen bed frame from the library" can now produce `replace_existing_row` drafts for matched current rows and scoped library components; Apply calls `replace_estimate_row_item_with_history` with expected row revision protection and a validated replacement payload. Current-route delete prompts such as "Delete the existing bed row from this estimate" can now produce `delete_existing_row` drafts for matched current rows; Apply calls `delete_estimate_row_item_with_history` with expected row revision protection. Current-route template row-copy prompts such as "Copy the bedroom paint row from the condo starter template into this estimate" can now produce `copy_template_row` drafts for matched template row previews and an existing Area Node; Apply calls `insert_estimate_row_item_with_history` with copied template-row snapshot metadata. Current-route template prompts such as "Insert the 3 Bedroom Condo Starter template into this estimate" can produce `insert_template` drafts for a matched reusable template and Apply calls `insert_estimate_template_into_estimate_with_history` against the existing estimate Group Node. It does not create projects or estimates.
- `create_library_component` Draft/Apply is now a distinct confirmation-gated contract for prompts such as "Add a component to my library called Queen bed frame, category Furniture, unit set, cost 18000 pesos." It creates no project, estimate, tree, row, or template drafts. Apply verifies the signed draft token and authenticated workspace/user boundary, then calls `create_ai_package_library_components_with_history`, which requires the matching server-recorded Apply authorization row, records/replays through `ai_package_apply_commands`, and transactionally calls `create_cost_library_component` with server-derived workspace/user ids, Ask Flip metadata, and one default price option. The Ask Flip preview renders `Library components`, requires the same explicit review checkbox, and links to `/workshop/library` after successful Apply. A gated live smoke now proves the real UI/auth/database path persists the component, default price option, current cost entry, version/price/state history, completed Apply authorization row, and component-only Apply command row without creating project, estimate, or estimate-row side effects; the same smoke replays the exact Apply request body and proves the second Apply returns `idempotent_replay` without duplicating the component or apply-command row.
- Draft read tools use the already server-derived authenticated workspace id for selected-column reads and must not call workspace-bootstrap helpers that can create/update workspace or profile records.
- Draft responses include a server-signed HMAC draft token bound to the draft id/hash, authenticated user, workspace, provider/model, and expiry.
- Pending Draft previews can be revised or rejected before Apply by sending the verified draft boundary. Additive follow-ups continue through `mode: "draft"` with base-draft fields so scoped library components can be appended to the pending draft. Deterministic cost/removal refinements use `mode: "refine"`, verify the same base hash/token before any read tools, skip provider generation, return a fresh draft/hash/token with `productionWrite: false`, and audit metadata as `mode: "draft"` with refinement/revision fields. Rejected previews, including server-signed previews that are not Apply-eligible, use `mode: "feedback"` with the reviewed draft/hash/token, verify the same signed boundary, record metadata-only rejected-draft feedback as `mode: "draft"` audit, call no read tools/provider/Apply path, and close the preview so it cannot be applied or revised. Old UI previews are marked stale so their Apply button cannot be used after a newer refined preview exists.
- Apply mode requires explicit UI confirmation, verifies the signed draft token and draft hash, records a metadata-only server authorization row, validates the workspace boundary server-side, creates the project, estimate shell, tree nodes, and approved rows through the authenticated `public.create_project_estimate_package_with_history` RPC, and records metadata-only AI/estimate audit rows.
- The UI preview is available inside the Ask Flip footer assistant for package prompts such as "Assemble me a 3 bedroom package, budget is 5 million pesos." Natural project-plus-estimate creation wording such as "Make a project for me with an estimate sheet which is for a 3 bedroom condo unit" also routes to package-builder Draft mode, and current-route prompts such as "Fill this estimate with beds and water closets" route to the target-aware Draft path. Current-row update drafts are shown as row changes with patch summaries, current-row replacement drafts show the replacement component, current-row delete drafts show the matched row delete, current-template row-copy drafts show the copied row and source template, current-template insert drafts show expected template node/row counts, pending draft follow-ups can replace the preview before Apply, and successful Apply reports inserted, updated, replaced, deleted, and template-inserted rows separately. After successful Apply, the preview renders an explicit `Open estimate` link to the created/filled estimate path from the server-returned `projectId` and `selectedNodeId`, falling back to the project estimates list when no selected node is returned. Read-only account questions remain on `/api/ai/ask`.
- Memory/RAG remains off and provider-owned canonical memory is not used. A default-off package-builder memory slice exists behind `AI_PACKAGE_BUILDER_MEMORY_ENABLED`: accepted Apply and rejected feedback can record safe structured library-item/template source signals, read tools can summarize them through authenticated workspace/user filters, and deterministic Draft can use them only as ranking hints. The local migration `20260528103341_ai_package_builder_memory.sql` has not been applied to the linked Supabase remote in this slice.
- Apply uses `ai_package_apply_commands` for idempotency. The package Apply RPC derives the acting user from `auth.uid()`, is granted to `authenticated`, and rejects direct calls unless the route first records a matching `ai_action_runs` authorization row after signed-token and confirmation checks. The normal production Apply path uses the user-scoped Supabase server client; the only service-role use in this path is the established metadata-only audit write for that authorization row. The linked Supabase remote has the AI audit foundation migration and package Apply RPC migration applied and repaired into migration history.
- Historical estimate rows are not treated as live supplier-priced sources and do not create linked library rows. When used by deterministic Draft, they become review-required allowance rows with historical-precedent warnings and metadata-only source labels.
- Comparable prior estimate packages are Draft-only room/row/cost/source-coverage hints. They can extend the proposed room program and create review-required allowance precedents, but they do not authorize linked supplier-priced rows or bypass Apply freshness checks.

## Recommended direction

Build an **Estimate Copilot** with three explicit modes:

1. **Ask**: answer questions about the current project, estimate, library, templates, and app workflow using read-only tools.
2. **Draft**: produce structured proposed changes, including project briefs, estimate tree nodes, row items, budget allocation, exclusions, assumptions, and uncertainty flags.
3. **Apply**: after explicit user confirmation, execute validated server-side actions that create or edit app records and write an audit trail.

Default model policy as of the fourth pass on 2026-05-23, modified by the current user override for the package-builder implementation:

- **Primary long-term path:** OpenAI Responses API, `gpt-5.5`, `reasoning.effort: medium`, through an Archestimator-owned provider adapter for tool-heavy estimate creation/editing, budget reasoning, and Apply-adjacent planning.
- **OpenAI cost lane:** `gpt-5.4-mini` only for routing, extraction, title/summary generation, library-search synthesis, and simple read-only Ask turns after evals prove quality.
- **DeepSeek lane:** temporarily allowed by explicit user override for read-only Ask and package-builder Draft with scoped/minimized data only. Server code still owns validation and Apply; the model never mutates records directly.

The implementation strategy is **provider-ready, app-tool-first**: keep app tools, schemas, evals, audit logs, and UI events provider-neutral. DeepSeek is the temporary Draft provider because the current user task explicitly approved it; replacing it with OpenAI Responses should only require implementing the same package-builder provider contract and switching provider construction.
